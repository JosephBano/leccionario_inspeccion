# 01 — Arquitectura

## Topología: client–server

Dos aplicaciones desplegables por separado, acopladas solo por un contrato HTTP/JSON.

```
┌──────────────────────────┐        HTTPS / JSON        ┌──────────────────────────┐
│  Frontend Angular 21     │  ───────────────────────▶  │  Leccionario.Api (net8)  │
│  SPA, sin estado servidor│  ◀───────────────────────  │  ASP.NET Core Web API    │
│  JWT en memoria + refresh│        Bearer JWT          │  Stateless               │
└──────────────────────────┘                            └────────────┬─────────────┘
                                                                     │ EF Core 8
                                                                     │ Pomelo MySQL
                                                              ┌──────▼──────┐
                                                              │ MySQL 5.7.21│
                                                              │  sigafi_es  │
                                                              └─────────────┘
```

Reglas de la frontera:

- El frontend **nunca** habla con MySQL. Toda consulta pasa por la API.
- La API es **stateless**: no hay sesión en servidor, la identidad viaja en el JWT.
- El navegador nunca recibe entidades de dominio — solo DTOs.

## Capas del backend

Clean Architecture pragmática, con la misma disposición física que
`BienestarInstitucional.Api` para que el equipo no cambie de mapa mental.

```
Leccionario.Api/
├── Domain/
│   └── Entities/          ← PLANO, autogenerado. Sin subcarpetas ni features.
├── Application/
│   ├── <Feature>/
│   │   ├── Services/      ← Casos de uso. Aquí vive la regla de negocio.
│   │   ├── DTOs/          ← Contratos de entrada/salida
│   │   └── Interfaces/    ← Puertos que Infrastructure implementa
│   └── Common/            ← Formatters, excepciones de aplicación, helpers puros
├── Infrastructure/
│   ├── DbContexts/        ← sigafi_esContext (autogenerado)
│   ├── Repositories/      ← Acceso a datos cuando la consulta no es trivial
│   └── Reporting/         ← Generación de Excel/PDF
├── Controllers/           ← HTTP only: validar, delegar, mapear respuesta
├── Extensions/            ← AddInfrastructureLayer, AddApplicationLayer, AddJwtAuthentication…
└── Middlewares/           ← Excepciones, auditoría, security headers, rate limiting
```

### Regla de dependencia

```
Controllers ──▶ Application ──▶ Domain
                     ▲
Infrastructure ──────┘   (implementa las interfaces de Application)
```

- `Domain` no referencia nada.
- `Application` no referencia `Infrastructure` **por tipo concreto**; solo por interfaz.
  Excepción aceptada y heredada de Bienestar: los servicios de aplicación inyectan
  `sigafi_esContext` directamente para consultas de lectura. Se admite porque
  `sigafi_es` es una base legacy compartida y un repositorio por entidad sería ruido
  sin beneficio. **No** se admite para escrituras de asistencia: esas pasan por
  `IAsistenciaRepository` para poder testearse sin base.
- `Controllers` no contiene lógica de negocio. Si un controller tiene un `if` que
  decide algo del negocio, ese `if` va al servicio.

### Por qué `Domain/Entities` es plano

Las entidades las genera **EF Core Power Tools** por scaffolding desde `sigafi_es`
(igual que en Bienestar: 83 archivos, un archivo por tabla, todos en
`Domain/Entities/`, con la cabecera `<auto-generated>`). Cualquier clasificación por
features se perdería en la siguiente regeneración. Ver
[`05-lineamientos-backend.md`](05-lineamientos-backend.md#regeneración-de-entidades).

## Capas del frontend

```
src/app/
├── core/          ← Singletons: AuthService, interceptors, guards, api client
│   ├── auth/
│   ├── guards/
│   ├── interceptors/
│   └── models/
├── features/
│   ├── auth/          ← Login
│   ├── docente/       ← Mis paralelos, pasar lista
│   ├── inspector/     ← Consultas y reportes
│   └── dashboard/
├── shared/        ← Componentes, pipes y utilidades reutilizables
└── layout/        ← main-layout (shell autenticado) y auth-layout
```

Regla: `features/` puede importar de `core/` y `shared/`. `core/` y `shared/` **nunca**
importan de `features/`. Dos features no se importan entre sí — lo común sube a `shared/`.

## Flujo de una petición típica

`POST /api/asistencias/sesiones/{idSesion}` (docente marca lista)

1. `AuthenticationMiddleware` valida el JWT (HS256, secreto compartido ISTPET).
2. `AsistenciasController` — `[Authorize(Roles = "cplec_docente")]`, valida el DTO.
3. `AsistenciaService.RegistrarAsync(idSesion, marcas, idProfesorDelToken)`:
   - **Autorización de datos**: comprueba que `idSesion → idAsignacion` pertenece al
     distributivo activo del `idProfesor` del token. Si no → `ForbiddenException`.
   - Valida que cada `idMatricula` pertenezca al paralelo de esa asignación.
   - Valida la ventana de edición (ver [`04-contrato-api.md`](04-contrato-api.md)).
   - Persiste vía `IAsistenciaRepository` (upsert transaccional).
4. `AuditMiddleware` registra la operación.
5. Respuesta `200` con el estado consolidado de la sesión.

El paso 3 (autorización de datos) es la parte que más tests unitarios debe tener.
